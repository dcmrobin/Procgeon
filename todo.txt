BUG -> CAUSE NOTES FOR FUTURE FIXING SESSIONS
============================================

2. Enemies dodge while player is invisible
Cause: the avoidance / projectile-dodging logic in updateEnemies() runs without checking invisibleRingsNumber and without
checking enemies[i].isFriend. That allows enemy movement to react to the player even when the player should be hidden, and also
allows friendly enemies to move out of the way of the player's bullets.

3. Clock enemy death leaves stale world state
Cause: clockX and clockY are set from the living clock enemy, but there is no reset when the clock dies. Nearby enemies continue
using the last known clock position as a proximity trigger, so they remain active and move freely after the clock is gone.

4. Ring identification / amnesia metadata mismatch
Cause: ring attributes are tracked with parallel arrays (ringEffects[] / ringDescriptions[]) and the item carries an index but not
a fully reliable source-of-truth record. When item state is copied, reset, or forgotten, the display name/description can
diverge from the actual effect state. Screens and item info use the stale names/descriptions rather than a single authoritative
item state.

5. Amnesia scroll only partially resets item metadata
Cause: resetPotionNames() and some inventory-page resets are implemented in a piecemeal way, but ring and scroll metadata are not
fully reset in one place. This leaves some item entries with names that are reset while their descriptions or original names remain
stale, producing the inconsistent UI bug.

6. Save / progression flags are too spread out
Cause: game progression and encounter flags are saved in SaveData and also read/written through many globals in Utils.cpp,
Dungeon.cpp, Screens.cpp, and Gameloop.cpp. This makes it easy to save the wrong phase or keep a cancelled encounter state alive
across level transitions and reloads.

7. Friendly enemy / hostile enemy targeting logic is mixed into generic chase logic
Cause: the AI branch in updateEnemies() treats isFriend as an afterthought while also switching target goals and chase toggles based
on invisibleRingsNumber and nearby hostiles. This means friend/enemy combat relationships are inferred from ad hoc checks instead
of clearer adversary state, leading to odd follow-target behavior and contradictory screens.

8. Item effects are resolved by comparing strings in several places
Cause: several status checks in Inventory.cpp compare itemResult strings or ring names to detect effect types (for example, "You
feel restored!" or ring names like "Ring of Aggravation"). String-based effect detection is brittle and can fail or misclassify
when descriptions are renamed, forgotten, or partially reset.
